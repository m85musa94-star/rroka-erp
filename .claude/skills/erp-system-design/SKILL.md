# تصميم منظومة RRoka ERP

المنظومة ليست برنامجًا لشاشات؛ هي **نظام رقابة مالية** يُشغِّل نشاطًا. كل قرار تصميم يُقاس بسؤال واحد:
**هل يبقى الرقم الناتج صحيحًا وقابلًا للتتبع حتى لو أخطأ المستخدم أو الكود؟**

## ١. طريقة العمل مع صاحب المشروع (قبل أي كود)

1. **افهم الدورة كاملة** قبل الشاشة: المستند ← الاعتماد ← القيد ← التقرير ← المطابقة. اسأل: من يُدخل؟ من يعتمد؟ ماذا يحدث للدفاتر؟
2. **اعرض قبل التنفيذ**: شكل الشاشة، النتائج، الأثر على القيود، وما يتغير في الضوابط. صاحب المشروع يقرر.
3. **خيارات لا رأي مجرد**: عند قرار معماري قدّم (أ/ب/ج) بالتكلفة والخطر والأثر، ثم توصية واحدة بسببها.
4. **صفر افتراضات**: لا أرقام ولا معدلات ولا حقول API غير مُتحقَّق منها. المجهول يُعرض «غير مُفعَّل» أو «—» لا صفرًا.
5. **إجابات قصيرة** بالعربية المهنية، وجدول عند المقارنة.
6. أي تغيير لقاعدة حاكمة في `CLAUDE.md` يُسجَّل قرارًا مؤرخًا في `docs/PROJECT_CONTEXT.md`.

## ٢. البنية: نواة + وحدات نشاط

| الطبقة | المحتوى | القاعدة |
|---|---|---|
| **النواة** | دليل الحسابات والقيود والفترات والقوائم، الخزينة والعهد، العملاء والموردون، المصروفات والمشتريات، فواتير العملاء والتحصيل، الضريبة، الموظفون، الصلاحيات، التقارير، الاستيراد، الاستثناءات | مشتركة لكل شركة؛ لا تعتمد على أي وحدة |
| **وحدات النشاط** | التصنيع حسب الطلب (موجودة)، المقاولات (جزئية: ينقصها المستخلصات والمحتجزات والدفعات المقدمة ومقاولو الباطن)، التجارة (غير موجودة: أصناف وأسعار بيع، أوامر بيع وتسليم، مخزون تام وتكلفته، مستودعات) | كل وحدة تعتمد على النواة فقط، فيمكن تشغيل أي مزيج |

الوحدة تتصل بالنواة عبر **المستند المحاسبي** فقط: مستند يُعتمد فيُرحَّل بقيد عبر `fn_post_document`. لا تكتب وحدة في جداول وحدة أخرى.

## ٣. حدود التخصيص (بالإعدادات لا بالبرمجة)

| المستوى | يُسمح؟ |
|---|---|
| بيانات المنشأة (الاسم، الشعار، ورق الطباعة، الرقم الضريبي، بداية السنة، دورية الإقرار، بادئات الترقيم) | نعم |
| تفعيل الوحدات حسب النشاط | نعم |
| قوالب النشاط (دليل حسابات، أدوار ترحيل، تصنيفات، مراكز تكلفة) تُعدَّل بعد الإنشاء | نعم |
| سياسات تشغيلية (مخزون تام مسموح؟ ورقة تكلفة إلزامية؟ منع الاعتماد الذاتي؟ حد اعتماد) | نعم، **بشرط أن تشدد الرقابة أو تختار بين بدائل صحيحة محاسبيًا** |
| حقول إضافية على البيانات الأساسية | محدود؛ لا تدخل في أي حساب مالي |
| محرر سير عمل أو معادلات أو تقارير حر | لا |
| كود أو نسخة خاصة بشركة | لا، مطلقًا |

**ثابت لا يُخصَّص أبدًا:** توازن القيد، قفل الفترات، الترقيم بلا فجوات، سجل التدقيق، منع تعديل المعتمد، قفل الإقرار الضريبي، عزل الشركات، «المجهول ليس صفرًا».

## ٤. مبادئ الرقابة (Control by design)

1. **القاعدة في قاعدة البيانات** (Trigger/Constraint) **وفي الـ API** معًا، لا في الواجهة. الرفض يُرفع بـ `RROKA_*` ويظهر 422 برسالة مترجمة.
2. **دورة المستند**: مسودة ← معتمد (نهائي) أو ملغى. المعتمد لا يُعدَّل؛ يُصحَّح بمستند عكسي أو إشعار. الحذف للمسودة فقط.
3. **قيد واحد لكل مستند**، يكتبه النظام فقط (`fn_journal_auto_insert`)، ولا يُنشأ أو يُعكس يدويًا. الاستبعاد من الترحيل بسبب مكتوب.
4. **الإلحاق لا التعديل** للسجلات الرقابية: المعدلات المؤرخة، الصور بعد الاعتماد، دفعات الاستيراد، سجل التدقيق.
5. **فصل المهام**: الإدخال والاعتماد صلاحيتان؛ الاعتماد الذاتي يظهر استثناءً للمراجعة.
6. **كل رقم قابل للتتبع**: من التقرير ← القيد ← المستند ← صورته ← من أدخله واعتمده (سجل النشاط).
7. **الاستثناءات بدل المراجعة الشاملة**: كل خلل محتمل فحصٌ في `Exceptions::definitions()` بإجراء يعالجه، وما يُفسد الإقفال يمنعه في قاعدة البيانات.
8. **الإدخال الجماعي يمر بالمسار نفسه**: الاستيراد يستدعي إجراء الحفظ ذاته؛ لا قواعد موازية.

## ٥. تعدد الشركات (عند تقريره)

- **الخيار الافتراضي**: قاعدة واحدة، عمود `company_id` في كل جدول أعمال، و**Row-Level Security** مع `FORCE ROW LEVEL SECURITY` ودور تطبيق ليس مالك الجداول، وسياق الشركة محلي للمعاملة (مثل `rroka.user_id`).
- **مفاتيح أجنبية مركّبة** تتضمن `company_id` فيستحيل ربط سجلين من شركتين.
- **ترقيم وفترات وإعدادات وتسلسل قيود** مستقلة لكل شركة.
- **اختبارات عزل إلزامية**: محاولة قراءة وتعديل وربط بيانات شركة أخرى يجب أن تفشل، في SQL وفي الـ HTTP.
- **النسخ الاحتياطي** أصعب نقطة: أداة تصدير/استرجاع لكل شركة. لعدد قليل من الشركات الحساسة: قاعدة مستقلة لكل شركة بدل ذلك.

## ٦. قائمة الإنجاز

أي وحدة أو شاشة أو مستند جديد لا يكتمل قبل المرور على `references/checklist.md` بندًا بندًا.

## ٧. علامات خطر توقف التنفيذ وتستدعي سؤال صاحب المشروع

- رقم مالي سيُبنى على حقل أو معدل غير مُتحقَّق منه.
- إعداد سيُضعف ضابطًا قائمًا.
- تعديل يمس بيانات حقيقية معتمدة أو مرحَّلة.
- تعارض مع قاعدة حاكمة في `CLAUDE.md`.
- قرار معالجة محاسبية أو ضريبية له أكثر من بديل مقبول (اعرض البدائل، والمرجع النظامي الحالي للضريبة لا الذاكرة).
